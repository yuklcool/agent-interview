## 06-01. RAG 里 Chunk 切大切小各有什么坑？实际怎么切业务文档

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否能把 RAG 当成完整检索系统而不是“向量库 + Prompt”。从解析、Chunk、索引、Query、召回、融合、重排、版本、权限、评测到多模态，每一层都可能成为瓶颈。

### 2. 核心结论

Chunk 的目标不是统一字数，而是保持“一个块表达一个完整业务语义”。

### 3. 深入原理：从概念讲到机制

Chunk 太小会切断前提和结论、表头和数据、条款标题和正文；太大则把多个主题混在同一 embedding 里，向量区分度下降，同时浪费上下文。优先按文档结构切：章节→小节→段落/表格/FAQ/函数，再按 token 上限二次切。Overlap 只在确实存在跨段语义依赖时使用，不要机械叠加。

* Chunk 优化目标是“检索可区分性 × 语义完整性 × 上下文成本”。结构优先于固定字符数：规范按条款、代码按函数/类、表格按表头+行组、FAQ 按问答。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 对每种文档类型单独做 Query-Doc eval，比较 chunk size/overlap 对 Recall@K 和 answer grounding 的影响，而不是凭经验定 500 字。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

在照明/企业文档中，我会把 FAQ 保持一问一答；规范/合同按条款标题+正文；表格保留表头和相关行；SQL Schema 按表定义；故障流程按节点或步骤组。metadata 保存文档 ID、版本、章节路径、业务类型、权限范围、生效时间。初始 chunk 可以从 300-800 tokens 试，但最终看 Recall/nDCG 和真实问答效果。

### 6. 失败模式与 Trade-off

* 只调 TopK，不建立真实 Query-Doc 评测集。
* 权限过滤放到生成阶段，导致越权数据已经被召回。
* 换 embedding 模型却不重建向量。

### 8. 面试官可能继续追问

为什么不固定 500 字？——中文字符数和 token/语义边界不一致。 表格怎么切？——保留表头、主键/单位，必要时行组化并重复表头。

* 如果这个方案失败，系统最后会收敛到什么状态？
* 哪些属于模型软决策，哪些必须由代码硬约束？
* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

“Chunk size 只是参数，真正要优化的是语义完整度和检索指标。我的做法是先结构切分，再按 token 做二次切分；不同文档类型用不同策略，不会一刀切 500 字。”

## 06-02. 混合检索怎么融 BM25 和向量？RRF 还是别的

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否能把 RAG 当成完整检索系统而不是“向量库 + Prompt”。从解析、Chunk、索引、Query、召回、融合、重排、版本、权限、评测到多模态，每一层都可能成为瓶颈。

### 2. 核心结论

第一版优先 Filter → BM25 + Dense → RRF → ReRank；数据足够后再学权重。

### 3. 深入原理：从概念讲到机制

BM25 对精确术语、编号、设备码非常强；Dense 对同义表达、语义相近更强。直接把 BM25 score 和 cosine score 相加通常不稳，因为量纲不同。RRF 只依赖排名，公式是 Σ1/(k+rank)，工程上稳健、调参少。之后如果有标注数据，可以做分数归一化、加权融合或学习排序。

* BM25 和 Dense 互补：前者抓精确词/编号，后者抓语义。RRF 用 rank 融合避免分数量纲问题，适合作为稳定 baseline。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 流程最好是 metadata/permission filter→BM25 TopK + Dense TopK→RRF→cross-encoder rerank→TopN。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

照明业务里道路名、设备号、告警码偏 BM25；用户口语化问法偏 Dense。先用权限/项目 metadata filter 缩小集合，再各自 TopK，RRF 合并，再交给 cross-encoder reranker。权限过滤要尽量前置，不能先跨权限召回再让 LLM“自觉过滤”。

### 6. 失败模式与 Trade-off

* 只调 TopK，不建立真实 Query-Doc 评测集。
* 权限过滤放到生成阶段，导致越权数据已经被召回。
* 换 embedding 模型却不重建向量。

### 8. 面试官可能继续追问

RRF 的 k 怎么选？——它控制头部排名差异敏感度，一般从常用默认值开始，再用离线集调。 什么时候不用 RRF？——有大量标注数据、检索器分数可校准时可做 learned fusion。

* 如果这个方案失败，系统最后会收敛到什么状态？
* 哪些属于模型软决策，哪些必须由代码硬约束？
* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

“我默认用 RRF 做稳健基线，因为 BM25 和向量分数不同量纲，RRF 用排名融合比较稳定。等真实标注数据够了，再考虑归一化加权或学习排序。”

## 06-03. ReRank 上线前后召回质量怎么量化

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否能把 RAG 当成完整检索系统而不是“向量库 + Prompt”。从解析、Chunk、索引、Query、召回、融合、重排、版本、权限、评测到多模态，每一层都可能成为瓶颈。

### 2. 核心结论

必须区分“召回能力”和“排序质量”：ReRank 主要改善候选内部排序。

### 3. 深入原理：从概念讲到机制

第一阶段检索看 Recall@K、HitRate@K；ReRank 前后看 MRR、nDCG@K、Precision@K、Top1/Top3 命中。比如正确文档从第 8 提到第 1，Recall@10 没变化，但 MRR/nDCG 显著提升，这才是 ReRank 的价值。线上还要看引用正确率、groundedness、用户追问率、任务完成率。

* ReRank 不能找回未召回文档，所以要分别看 Recall@K 和排序指标 MRR/nDCG。固定候选集对比才知道增益来自 rerank。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 把模型输出变成结构化 contract，Runtime 校验后才进入执行。
* 为关键状态引入 run_id / step_id / version / status，使它可持久化、可恢复、可审计。
* 对有副作用行为增加 policy、幂等、deadline、trace 和明确的 failure type。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

我会建立真实 Query-Doc 标注集，同一候选集分别走无 rerank / 有 rerank，保持 embedding、检索 topK、prompt、模型不变。上线先 shadow 或小流量，记录 reranker_version 和最终答案指标，避免只看离线排序。

### 6. 失败模式与 Trade-off

* 只调 TopK，不建立真实 Query-Doc 评测集。
* 权限过滤放到生成阶段，导致越权数据已经被召回。
* 换 embedding 模型却不重建向量。

### 8. 面试官可能继续追问

如果 Recall@K 很低，先优化什么？——先优化召回器/Chunk/Query rewrite，而不是期待 reranker“变出”没召回的文档。 没有标注怎么办？——先做小规模人工标注和线上点击/引用弱监督。

* 如果这个方案失败，系统最后会收敛到什么状态？
* 哪些属于模型软决策，哪些必须由代码硬约束？
* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

“ReRank 不是提高第一阶段 recall 的万能药，它主要重新排序候选。我会分别看 Recall@K 和 MRR/nDCG，并用固定候选集做对照实验，避免把召回改善和排序改善混在一起。”

## 06-04. RAG 知识库版本变了，线上怎么热更不闪断

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否能把 RAG 当成完整检索系统而不是“向量库 + Prompt”。从解析、Chunk、索引、Query、召回、融合、重排、版本、权限、评测到多模态，每一层都可能成为瓶颈。

### 2. 核心结论

新旧索引并存、预热、灰度、原子切换版本指针，绝不在生产索引上原地重建。

### 3. 深入原理：从概念讲到机制

标准发布流程：build v2 → embedding/index → 离线评测 → warmup → shadow/canary → alias/current_version 原子切换 → 观察 → 保留 v1 回滚。长会话可以固定 knowledge_version，避免同一对话前后引用不同规则。

* 知识库更新按软件发布处理：build v2→离线 eval→warmup→shadow/canary→alias 原子切换→保留 v1 回滚。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 长会话可 pin knowledge_version，避免同一会话前后规则突然变化；紧急规则另做显式 override。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

退改签、运维规范等规则更新尤其要带 version/effective_time。检索 Tool 或 Session metadata 记录 knowledge_version；新旧索引双跑评测，异常随时回滚。

### 6. 失败模式与 Trade-off

* 只调 TopK，不建立真实 Query-Doc 评测集。
* 权限过滤放到生成阶段，导致越权数据已经被召回。
* 换 embedding 模型却不重建向量。

### 8. 面试官可能继续追问

为什么会话要固定版本？——避免一轮说旧规则，下一轮突然变成新规则。 如何处理紧急规则？——允许显式 override，但要在回答中标注生效时间/版本。

* 如果这个方案失败，系统最后会收敛到什么状态？
* 哪些属于模型软决策，哪些必须由代码硬约束？
* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

“我会把知识索引当一次软件发布：先 build，再 warm，再 canary，最后切 alias；旧版本保留一段时间可快速回滚。”

## 06-05. Embedding 模型怎么和召回场景对齐？怎么做领域微调或替换

### 2. 核心结论

先用真实 Query-Doc 评测选型，效果不足再微调；换模型通常等价于重建向量索引。

### 3. 深入原理：从概念讲到机制

比较 Recall@K、HitRate、MRR/nDCG，同时关注语言、专业术语、长文本能力。先试 query rewrite、hybrid retrieval、rerank；仍不足再用 hard negative 做对比学习或领域微调。不同 embedding 模型的向量空间不能混用。

* 选型看真实 Query-Doc 指标、语言、领域术语、长度、成本和吞吐。换 embedding 意味着新向量空间，通常必须重建索引。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 在微调前先检查 chunk/query rewrite/hybrid/rerank，因为很多“embedding 不行”其实是检索链路其他环节的问题。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 6. 失败模式与 Trade-off

* 只调 TopK，不建立真实 Query-Doc 评测集。

* 换 embedding 模型却不重建向量。

* 典型原因是 recall 太宽、rerank 弱、文档冲突/过期、上下文排序差、Prompt 无法聚焦。先看检索结果而不是先换模型。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 对每条 Query 做 retrieval trace：候选、分数、版本、权限、最终送入模型的 TopN；逐层定位。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

结合城市照明/企业知识库，可以直接用道路名、设备编号、报警码、规范条款和多表业务关系构造真实 Query-Doc / Tool eval，避免只用通用公开数据评测。

### 6. 失败模式与 Trade-off

* 只调 TopK，不建立真实 Query-Doc 评测集。
* 权限过滤放到生成阶段，导致越权数据已经被召回。
* 换 embedding 模型却不重建向量。

## 06-16. 如何防止“补检索→还不够→再补检索”无限循环？

## 06-17. 多模态 Embedding 做图文检索时，怎么避免视觉相似压过业务语义？
