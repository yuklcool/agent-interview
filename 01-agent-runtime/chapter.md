## 01-01. 讲一个落地过的 AI Agent 项目：从用户提问到最终回答完整链路

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否理解 Agent 不是一个“会聊天的模型”，而是一套带状态、工具、循环、停止条件和工程边界的运行系统。回答时要能区分“模型能力”“Runtime/Harness 能力”“业务工作流能力”，并能解释为什么某些开放决策适合模型、某些确定性约束必须下沉到代码。

### 2. 核心结论

不要回答成“用户→LLM→Tool→答案”；要把 Session、Context、Tool 校验、回注、持久化和 Agent Loop 都讲出来。

### 3. 深入原理：从概念讲到机制

Agent 的运行链路可以拆成五层：入口与会话、上下文构造、模型决策、工具执行、结果回注与持久化。Durable Transcript 是完整事实记录；Model-facing Context 是本轮真正喂给模型的投影，两者要区分。Tool Call 不是执行本身，模型只提出动作，Runtime 才拥有执行权。

* 完整链路至少要分成“入口与身份、Session、Context Projection、LLM 决策、Tool Execution、Observation 回注、持久化/恢复、输出”八个边界。每个边界都要回答：输入是什么、谁有写权限、失败后如何恢复。
* Durable Transcript 和 Model-facing Context 必须分开：前者用于审计/恢复，是事实记录；后者是每一轮按 token budget 重新构造的模型视图。Tool Call 只是模型提出动作，真正副作用只能由 Runtime/业务 Service 执行。

```
用户→入口/Auth→Session→Context Build→LLM
                         ↓ Tool Call
                  Policy/Schema Check
                         ↓
                Tool/MCP/Service/DB
                         ↓ Tool Result
                  回注 LLM → Final
```

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 建议给每个 Run 生成 run\_id/turn\_id/iteration/tool\_call\_id，并在 Trace、日志、checkpoint 和业务调用中贯穿；这样一条失败链才能被复现。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

nanobot 中主流程由 AgentLoop 承接产品层会话与入口，核心循环下沉到 AgentRunner ；Session 由 SessionManager 管理，工具通过 ToolRegistry / execution 层执行，上下文治理由 Context 相关组件负责。你的自建前端通过 WebSocket 把 user/session/message 交给 nanobot，Tool 再接 Java 服务、数据库或 MCP。

### 6. 失败模式与 Trade-off

* 把 Agent 简化成“LLM + Tool”而忽略 Session/State/Loop。
* 用 Prompt 代替状态机和执行约束。
* 只讲正常路径，不讲停止、失败、恢复和审计。

### 7. 场景推演

```
用户：“昨晚哪些路灯能耗异常？分析原因”
  ↓ WebSocket
AgentLoop：解析 session / user / metadata
  ↓
Session + Summary + Recent Messages + Tool Schema
  ↓
LLM 第一次：决定 query_database
  ↓
Runtime 校验 Tool / 参数 / 权限
  ↓
SQL / Service 执行
  ↓
Tool Result 作为 observation 回注
  ↓
LLM 第二次：分析并可能继续调 get_device_history
  ↓
Final Answer + 持久化
```

### 8. 面试官可能继续追问

为什么不把 Tool Result 直接返回用户？——因为 Tool Result 是“事实观测”，还需要模型做语义整合。 为什么要区分 transcript/context？——为了长期记忆、审计和 Token 控制。

* 如果这个方案失败，系统最后会收敛到什么状态？
* 哪些属于模型软决策，哪些必须由代码硬约束？
* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

“我把 Agent 理解成一个循环运行系统：LLM 负责决策，Session/Context 负责状态，Tool Runtime 负责执行；每次 Tool Result 会作为 observation 回注模型，直到模型给出 final answer。完整历史持久化，但真正发给模型的上下文会按 token budget 做裁剪和压缩。”
源码/工程落点： nanobot/agent/loop.py；nanobot/agent/runner.py；nanobot/session/manager.py；nanobot/agent/tools/registry.py

## 01-02. 最近在看什么 AI 工程化？Spring AI 还是 LangGraph？说一个不喜欢的点

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否理解 Agent 不是一个“会聊天的模型”，而是一套带状态、工具、循环、停止条件和工程边界的运行系统。回答时要能区分“模型能力”“Runtime/Harness 能力”“业务工作流能力”，并能解释为什么某些开放决策适合模型、某些确定性约束必须下沉到代码。

### 2. 核心结论

选择框架看系统边界，不按流行度；你当前已有 nanobot Runtime，不需要 Java 再造第二套 Agent Runtime。

### 3. 深入原理：从概念讲到机制

Spring AI 的优势是与 Spring Bean、配置、Observability、VectorStore、HTTP Client 等生态融合自然；LangGraph 强在显式 State/Graph/Checkpoint，适合长流程和图式编排。两者的问题都在于：当需求进入细粒度权限、恢复、人工确认、长任务、复杂 trace 时，高层抽象往往不够，最终仍需自己的 Runtime/Orchestration contract。

* 不要把框架当 Agent 的“能力来源”。真正要比较的是状态模型、控制流、工具契约、checkpoint、observability、生态和团队栈。Spring AI 更像把模型能力嵌进 Spring 应用；LangGraph 更强调显式 state/graph。
* 如果已有 nanobot Runtime，再叠一套 LangGraph/Spring AI Agent Loop 往往造成双重状态、双重 retry、双重 trace。更合理的是确定一个 Runtime owner，其他框架只在适合的边界使用。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* Java 业务服务保留事务/权限；nanobot 管 Loop；需要确定性长流程时用工作流/状态机。这样模型供应商或 Runtime 变化不会迫使重写业务服务。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

你的架构已经有 nanobot 作为 Agent Loop，可以让 Java 侧聚焦业务 Tool/MCP、事务、权限、trace；如果某个业务确实需要确定性 DAG，再用 Java 工作流/状态机或独立 orchestrator，而不是强行把两套 Agent 框架叠在一起。

### 6. 失败模式与 Trade-off

* 把 Agent 简化成“LLM + Tool”而忽略 Session/State/Loop。
* 用 Prompt 代替状态机和执行约束。
* 只讲正常路径，不讲停止、失败、恢复和审计。
* 框架越高层，简单场景开发越快；但复杂恢复、人工确认和细粒度权限越容易碰到抽象边界。

### 8. 面试官可能继续追问

为什么不用 LangGraph 全包？——如果核心业务是 Java 微服务，引入 Python runtime 会增加部署和 observability 边界。 Spring AI 缺点？——复杂 Agent 状态和恢复能力不应完全依赖高层封装。

* 如果这个方案失败，系统最后会收敛到什么状态？
* 哪些属于模型软决策，哪些必须由代码硬约束？
* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

“我不按流行度选框架。我现在更关注 Runtime 边界：nanobot 管 Agent Loop，Java 管业务和事务；需要显式 DAG 时再引入工作流，而不是在一个系统里叠两套 Agent Runtime。”

## 01-03. DAG 工作流和自主 Agent 在订票订酒店场景怎么共存

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否理解 Agent 不是一个“会聊天的模型”，而是一套带状态、工具、循环、停止条件和工程边界的运行系统。回答时要能区分“模型能力”“Runtime/Harness 能力”“业务工作流能力”，并能解释为什么某些开放决策适合模型、某些确定性约束必须下沉到代码。

### 2. 核心结论

外层 DAG 保证交易确定性，内层 Agent 负责开放理解和推荐。

### 3. 深入原理：从概念讲到机制

搜索、解释、偏好匹配、候选排序适合 Agent；下单、锁库存、价格确认、用户确认、支付、出票、退款等有副作用步骤必须走确定状态机/DAG。一个 DAG 节点内部可以运行 Agent，但 Agent 不能绕过交易节点。

* 判断标准不是“复杂就 Agent、简单就 Workflow”，而是看步骤是否可预先枚举、是否允许开放探索、是否存在强副作用、是否要求可证明顺序。确定性高/风险高用 Workflow；开放搜索/解释/候选探索用 Agent。
* 最实用的架构通常是“外层确定性、内层开放性”：交易主链由 DAG/状态机控制，某些节点内部允许 Agent 自主搜索。

```
Agent：理解/搜索/排序
        ↓
Workflow：Quote→Lock→Confirm→Pay→Issue
        ↑
Agent 只在允许节点内发挥自由度
```

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 把 Workflow state 作为事实源；Agent 只能读取当前 state 和该节点允许的 Tool。像 Pay 只能从 CONFIRMED 状态进入，模型即使想跳步也执行不了。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

可以让 nanobot 在“查询候选方案”节点内部运行 tool loop；当进入“确认/支付/出票”节点时，只暴露该节点允许的工具，真正状态由 Java 工作流/订单系统管理。

### 6. 失败模式与 Trade-off

* 把 Agent 简化成“LLM + Tool”而忽略 Session/State/Loop。
* 用 Prompt 代替状态机和执行约束。
* 只讲正常路径，不讲停止、失败、恢复和审计。

### 7. 场景推演

```
Agent：理解需求 / 搜候选 / 排序
        ↓
DAG：Quote → Lock → Confirm → Pay → Issue
        ↑
Agent 可在某些节点内做搜索/解释
但不能跳过状态机节点
```

### 8. 面试官可能继续追问

* 如果这个方案失败，系统最后会收敛到什么状态？
* 哪些属于模型软决策，哪些必须由代码硬约束？
* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

“Agent 决定选什么、怎么找；DAG 决定怎么安全成交。开放式决策和确定性副作用要分层。”

## 01-06. CoT 和 ReAct 的核心区别是什么？

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否理解 Agent 不是一个“会聊天的模型”，而是一套带状态、工具、循环、停止条件和工程边界的运行系统。回答时要能区分“模型能力”“Runtime/Harness 能力”“业务工作流能力”，并能解释为什么某些开放决策适合模型、某些确定性约束必须下沉到代码。

### 2. 核心结论

CoT 是“只在已有信息里推理”，ReAct 是“推理—行动—获得新观察—再推理”的开放信息闭环。

### 3. 深入原理：从概念讲到机制

是否需要在推理过程中主动改变信息集，是两者最实用的判断标准。数学推理、静态文本分析可以只做内部推理；查数据库、搜索、执行代码、读取文件时，模型必须通过 Action 获得外部 Observation。工程上不要依赖显式暴露思维链，重点是模型决策与工具观察的交替状态。

* CoT 主要解决内部推理分解，ReAct 则把“推理—行动—观察”交替起来。关键差别不是有没有思考，而是 ReAct 把外部世界反馈纳入下一步决策。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* Executor 返回的不是一段自由文本，而应至少有 status、artifacts、evidence、error\_type、retryable。Planner 只根据这些结构化结果决定 continue/replan。

## 01-13. DAG 工作流和带环的 Agent Graph 有什么区别？什么时候必须允许环？

> 标签：理论、工程、实践

* DAG 适合一次性有向依赖，天然易做拓扑执行和完成性判断；带环 Graph 适合需要 retry、反思、补检索、replan 的场景。问题不是能不能有环，而是环必须有退出条件和预算。

## 01-16. Harness 和“把 Agent 能力训练进模型”这两条路线是什么关系？

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否理解 Agent 不是一个“会聊天的模型”，而是一套带状态、工具、循环、停止条件和工程边界的运行系统。回答时要能区分“模型能力”“Runtime/Harness 能力”“业务工作流能力”，并能解释为什么某些开放决策适合模型、某些确定性约束必须下沉到代码。

### 3. 深入原理：从概念讲到机制

* 训练可以提高先验能力和默认行为，例如工具格式遵循、领域知识、规划习惯；Harness 则提供运行时硬约束和外部反馈。两者不是替代关系。
* 能通过训练降低频繁错误的软行为可以训练；涉及权限、金额、删除、状态机顺序的硬约束必须留在 Runtime。因为模型永远存在分布外输入和概率性失败。
