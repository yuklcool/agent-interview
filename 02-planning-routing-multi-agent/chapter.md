## 02-01. 意图识别是模型做还是分类器做？为什么

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否真正理解任务分解、路由、多 Agent 协作不是“多开几个模型”，而是状态、责任、上下文、工具权限、取消与聚合的系统设计问题。面试官通常会追问失败时如何收敛、用户改口怎么处理、异步结果如何防止污染新计划。

### 2. 核心结论

采用“确定性路由 + LLM 语义路由”的混合方案，不做非黑即白。

### 3. 深入原理：从概念讲到机制

传统分类器适合类别稳定、高频、样本足够的单标签任务；LLM 适合长尾、组合意图、强上下文依赖。Agent 的用户请求常常是“查询+分析+动作”组合，不是一个固定标签。工程上应把高风险命令、权限入口、系统命令做确定性规则，把开放自然语言交给 LLM；如果流量大，还可以在 LLM 前加轻量 classifier 做一级分流。

* 意图识别不要设计成一个孤立分类器问题。真正目标是“选择后续处理策略”。因此输入不仅有当前文本，还可能需要 Session 状态、用户角色、产品入口和已完成步骤。
* 高频稳定意图适合规则/轻量分类器；长尾组合意图适合 LLM；高风险动作要在执行层重新做 policy 校验，不能把分类结果当授权。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 线上需要维护 confusion matrix：哪些意图最容易混淆、错分成本多大。高成本错分要优先用规则或独立确认兜底。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

nanobot 的普通 Tool 选择主要由模型结合 Tool Schema 决定，但命令、Tool 是否可用、权限、workspace 边界都不能交给模型。你的项目可把“固定系统命令/菜单动作”在 Java/前端确定性路由，业务自然语言进入 nanobot。

### 6. 失败模式与 Trade-off

* 拆了很多 Agent 但没有明确 owner 和共享状态。
* 所有角色都拿全量上下文和全量工具，成本和权限面一起爆炸。
* 异步结果没有版本号/任务号，用户改口后旧结果仍写回。

### 8. 面试官可能继续追问

追问“分类器精度更高怎么办？”——高频固定意图就前置分类器，开放意图仍给 LLM。 追问“模型识别错会不会误操作？”——不会直接执行，Tool 层还有 schema/policy/risk 校验。

* 如果这个方案失败，系统最后会收敛到什么状态？
* 哪些属于模型软决策，哪些必须由代码硬约束？
* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

“我不把意图识别和执行权限绑死。固定、高频、风险高的入口走规则或分类器；开放、组合、长尾意图交给 LLM。即使模型识别错了，最终 Tool 执行仍要过代码层权限和参数校验。”

## 02-02. 意图歧义或漏识别怎么兜底？举一个旅游组合意图

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否真正理解任务分解、路由、多 Agent 协作不是“多开几个模型”，而是状态、责任、上下文、工具权限、取消与聚合的系统设计问题。面试官通常会追问失败时如何收敛、用户改口怎么处理、异步结果如何防止污染新计划。

### 2. 核心结论

用“最小澄清”原则：只有缺失信息会改变执行正确性时才问用户。

### 3. 深入原理：从概念讲到机制

兜底可分三层：能安全推断就继续；非关键参数给默认值；关键参数缺失或高风险时做澄清。组合意图先拆成任务图，再判断哪些参数是全局约束、哪些只是子任务偏好。避免把所有槽位都问一遍，否则 Agent 会变成表单。

* 澄清的目标不是收集完整信息，而是降低“错误执行风险”。可以用 expected value：这个缺口如果猜错，会不会改变结果/产生副作用？只有高影响缺口才阻塞。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 为澄清设置 budget，例如最多 1~2 个问题；其余使用默认值并在答案中显式标注假设。这样不会把 Agent 退化成表单。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

比如用户说“周六台北一日游，上午去故宫，中午吃牛肉面，下午下雨就安排室内，晚上 21 点高铁”。可以拆成日期解析、POI、餐厅、天气、路线、离站时间。若没说出发点而它明显影响路线，就问一次；午餐预算不关键，可以按中档默认。

### 6. 失败模式与 Trade-off

* 拆了很多 Agent 但没有明确 owner 和共享状态。
* 所有角色都拿全量上下文和全量工具，成本和权限面一起爆炸。
* 异步结果没有版本号/任务号，用户改口后旧结果仍写回。

### 7. 场景推演

```
用户请求
  ↓
Intent/Constraint Parse
  ├─ 日期
  ├─ POI
  ├─ 餐厅
  ├─ 天气条件
  └─ 高铁时间
  ↓
判断关键缺口
  ├─ 关键 → 最小澄清
  └─ 非关键 → 默认值继续
```

### 8. 面试官可能继续追问

如果 LLM 漏掉一个意图？——后续 Tool/结果验证和 Planner review 可以发现；高价值意图可加规则补充。 如何避免一直追问？——设置澄清预算和默认策略。

* 如果这个方案失败，系统最后会收敛到什么状态？
* 哪些属于模型软决策，哪些必须由代码硬约束？
* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

“我的原则不是把所有信息都问完整，而是只阻塞那些会改变执行正确性的关键缺口。组合意图先拆任务和依赖，能安全默认的就继续，只有真正影响路线、支付或高风险动作时才澄清。”

## 02-03. 场景：查明天上海飞北京最早航班，再推国贸附近酒店，怎么拆任务

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否真正理解任务分解、路由、多 Agent 协作不是“多开几个模型”，而是状态、责任、上下文、工具权限、取消与聚合的系统设计问题。面试官通常会追问失败时如何收敛、用户改口怎么处理、异步结果如何防止污染新计划。

### 2. 核心结论

先解析共享约束，再把独立搜索并行；依赖出现时再串起来。

### 3. 深入原理：从概念讲到机制

先解析“明天”的绝对日期和时区，明确“上海→北京”是城市级机场范围；然后拆成 Flight Search 和 Hotel Search 两个任务。酒店推荐只依赖目的地/国贸，不依赖具体航班，所以可并行。若用户再说“落地后 30 分钟能到酒店”，才引入到达机场和 ETA 依赖。

* 任务分解先找共享约束（日期、城市、预算、用户偏好），再识别依赖。航班搜索和国贸附近酒店在没有“落地后多久到酒店”的约束时可以并行；一旦加入到达机场/ETA，酒店排序就依赖航班结果。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* “最早”要定义排序口径，是起飞时间、到达时间还是总耗时；城市级搜索要覆盖多机场，避免模型只查一个机场后给出错误全局最优。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

在 nanobot 中，如果查询 Tool 标记 concurrency-safe，可以由一次模型响应并行执行多个工具；也可以在多 Agent 架构下用 Flight Worker / Hotel Worker。最终聚合器不直接返回原始 JSON，而是说明口径、最早航班、起降机场、酒店距离/评分/价格。

### 6. 失败模式与 Trade-off

* 拆了很多 Agent 但没有明确 owner 和共享状态。
* 所有角色都拿全量上下文和全量工具，成本和权限面一起爆炸。
* 异步结果没有版本号/任务号，用户改口后旧结果仍写回。

### 7. 场景推演

```
Resolve date/timezone/city scope
       ↓
   ┌───┴─────────────┐
   ↓                 ↓
Flight Search     Hotel Search
   ↓                 ↓
Rank earliest     Rank near Guomao
   └──────┬──────────┘
          ↓
Optional Route/ETA constraint
          ↓
Final synthesis
```

### 8. 面试官可能继续追问

最早是起飞最早还是到达最早？——默认计划起飞最早，但答案里明确口径。 上海/北京多个机场怎么处理？——城市级搜索后统一排序，不偷懒只查一个机场。

* 如果这个方案失败，系统最后会收敛到什么状态？
* 哪些属于模型软决策，哪些必须由代码硬约束？
* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

“我先解析共享约束，再把航班和酒店两个独立任务并行；只有用户增加落地时间/交通约束时才把它们串起来。最终答案明确‘最早’口径，不直接吐 Tool JSON。”

## 02-04. Agent 编排是 ReAct 还是 Plan-and-Execute？长任务为什么选后者或混合

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否真正理解任务分解、路由、多 Agent 协作不是“多开几个模型”，而是状态、责任、上下文、工具权限、取消与聚合的系统设计问题。面试官通常会追问失败时如何收敛、用户改口怎么处理、异步结果如何防止污染新计划。

### 2. 核心结论

短任务 ReAct，长任务 Plan-and-Execute，复杂 Step 内可以局部 ReAct。

### 3. 深入原理：从概念讲到机制

ReAct 优点是灵活、简单，缺点是长任务容易目标漂移、成本不可控、恢复困难。Plan-and-Execute 先把目标拆成 step/dependency/status，能明确并行、重试、完成条件；但过度图化也会降低灵活性。混合方式最实用：外层显式 Plan，内部 Worker 做局部探索。

* ReAct 的 state 隐含在对话轨迹中，适合短、局部、反馈快的任务；Plan-and-Execute 把全局目标和依赖显式化，适合长任务、并行和恢复。
* 生产里常用“外层 Plan，内层 ReAct”：Plan 负责 step/dependency/status，Worker 在单个 step 内自主调用工具；失败只局部 replan。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 选择依据可以量化：预期步骤数、依赖深度、副作用风险、是否需要并行、是否需要跨重启恢复。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

nanobot 的 AgentRunner 本质是 tool-using loop，不是通用 DAG Planner。所以如果旅行/运维长任务需要显式 plan，可以在上层维护 plan\_id、step、dependency、status；每个 step 交给 nanobot 运行 ReAct。

### 6. 失败模式与 Trade-off

* 拆了很多 Agent 但没有明确 owner 和共享状态。
* 所有角色都拿全量上下文和全量工具，成本和权限面一起爆炸。
* 异步结果没有版本号/任务号，用户改口后旧结果仍写回。

### 7. 场景推演

```
Planner
  ↓ 生成结构化 Plan
Step A ──┐
Step B ──┼→ Worker（局部 ReAct）
Step C ──┘
  ↓
Reviewer / State Update / Replan
```

### 8. 面试官可能继续追问

什么时候不用 Plan？——两三步可直接 ReAct 的简单任务不要过度设计。 Plan 是否让模型一次生成全部细节？——只生成必要结构，执行中允许局部 replan。

* 如果这个方案失败，系统最后会收敛到什么状态？
* 哪些属于模型软决策，哪些必须由代码硬约束？
* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

“我不是 ReAct 和 Plan-and-Execute 二选一。短任务直接 ReAct；长任务用结构化 Plan 管依赖和恢复；单个复杂 Step 内仍允许 Worker 做局部 ReAct。”

## 02-05. 多 Agent 怎么分工？Router / Planner / Worker / Reviewer 各自边界

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否真正理解任务分解、路由、多 Agent 协作不是“多开几个模型”，而是状态、责任、上下文、工具权限、取消与聚合的系统设计问题。面试官通常会追问失败时如何收敛、用户改口怎么处理、异步结果如何防止污染新计划。

### 2. 核心结论

角色越窄越好，避免所有 Agent 都能规划、执行、改状态。

### 3. 深入原理：从概念讲到机制

Router 负责流量和任务类型路由；Planner 拆目标、依赖和完成条件；Worker 执行一个具体 step；Reviewer 验证证据、约束和结果，不直接偷偷改业务事实。共享的是 Task State/Artifact，不是无限制工具权限。

* 最重要是责任边界：Router 不执行业务；Planner 不持有高风险 Tool；Worker 只处理一个 Step；Reviewer 验证但不偷偷修改业务事实。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 权限跟角色绑定：allowed\_tools、required\_scopes、context\_projection。共享的是 task\_state/artifact，不是完整聊天和全量工具。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

nanobot 可以用 SubagentManager 承载 Worker，但 Router/Planner/Reviewer 是上层业务角色，需要平台自己定义。每个 Worker 只拿当前 step 必要 context/tool。

### 6. 失败模式与 Trade-off

* 拆了很多 Agent 但没有明确 owner 和共享状态。
* 所有角色都拿全量上下文和全量工具，成本和权限面一起爆炸。
* 异步结果没有版本号/任务号，用户改口后旧结果仍写回。

### 8. 面试官可能继续追问

Reviewer 能不能自己修？——可以提出 retry/replan 建议，但不要绕过编排器直接做高风险动作。 多个 Worker 如何共享信息？——通过结构化 state/artifact 引用，不互相拷贝完整聊天。

* 如果这个方案失败，系统最后会收敛到什么状态？
* 哪些属于模型软决策，哪些必须由代码硬约束？
* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

“Router 决定去哪，Planner 决定怎么做，Worker 负责做，Reviewer 判断做得对不对；角色之间共享状态和产物，不共享无限制权限。”
源码/工程落点： nanobot/agent/subagent.py；nanobot/agent/loop.py

## 02-06. 场景：三个 Worker 并行查航班、酒店、签证，其中一个超时，最终结果怎么聚合

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否真正理解任务分解、路由、多 Agent 协作不是“多开几个模型”，而是状态、责任、上下文、工具权限、取消与聚合的系统设计问题。面试官通常会追问失败时如何收敛、用户改口怎么处理、异步结果如何防止污染新计划。

### 2. 核心结论

并行不是 all-or-nothing；聚合器要有 deadline、partial result 和 criticality policy。

### 3. 深入原理：从概念讲到机制

每个子任务状态至少有 SUCCESS/TIMEOUT/FAILED，并标记 required/optional。全局 deadline 到达时收集已完成结果；关键任务缺失则阻塞、降级或要求用户确认，非关键缺失则返回 partial success，并明确缺失项。不能为了“有答案”把超时项编出来。

* Fan-out/fan-in 需要定义 global deadline、per-worker timeout、required/optional、partial success policy。Aggregator 应根据 criticality 处理，不是简单 await all。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 异步 Worker 返回必须带 task\_id/step\_id/plan\_version；超时后晚到的结果要判断当前任务版本是否仍有效。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

nanobot 支持并发 Tool，concurrency-safe 的调用可并行；SubagentManager 也有并发管理。平台层仍要定义 per-worker timeout、required/optional 和 aggregate policy。例如签证政策决定能否出行，是强依赖；酒店超时可以先给航班并说明酒店暂未取回。

### 6. 失败模式与 Trade-off

* 拆了很多 Agent 但没有明确 owner 和共享状态。
* 所有角色都拿全量上下文和全量工具，成本和权限面一起爆炸。
* 异步结果没有版本号/任务号，用户改口后旧结果仍写回。

### 7. 场景推演

```
Global Deadline
```

## 02-07. 场景：用户中途改口“不要最早了，要最便宜”，原 Plan 怎么作废重规划

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否真正理解任务分解、路由、多 Agent 协作不是“多开几个模型”，而是状态、责任、上下文、工具权限、取消与聚合的系统设计问题。面试官通常会追问失败时如何收敛、用户改口怎么处理、异步结果如何防止污染新计划。

### 2. 核心结论

把用户新指令作为高优先级事件：旧目标相关未完成 step 作废，可复用 artifact 保留，生成新 plan\_version。

### 3. 深入原理：从概念讲到机制

不要从零重放整条任务。维护 plan\_id、plan\_version、goal、step/status/dependency。新需求到达后做 diff：哪些 step 失效、哪些结果仍可复用、哪些正在执行需要 cancel/ignore。旧异步结果必须携带 plan\_version，返回时若版本不匹配就丢弃，避免污染新计划。

* 用户新消息是高优先级外部事件。处理步骤是：识别目标差异→生成 plan diff→取消/忽略受影响的未完成步骤→复用仍有效 artifacts→生成新 plan\_version。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 取消不等于真的能终止外部 API，所以必须同时支持 cancellation token 和 version check。旧任务即使晚返回，也因版本不匹配被丢弃。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

nanobot 当前有 mid-turn pending message injection：同一 Session 正在执行时，新消息可以进入 pending queue，并在工具执行后等边界注入 AgentRunner，所以模型能感知“用户改口”。但 nanobot 本身没有通用 Plan 版本状态机；旅行 Planner 需要在上层补 plan\_id/version、cancellation token、artifact version。

### 6. 失败模式与 Trade-off

* 拆了很多 Agent 但没有明确 owner 和共享状态。
* 所有角色都拿全量上下文和全量工具，成本和权限面一起爆炸。
* 异步结果没有版本号/任务号，用户改口后旧结果仍写回。

### 7. 场景推演

```
Plan v1：最早航班
  ↓ 正在搜索
用户：“改成最便宜”
  ↓ pending message injection
Plan diff
  ├─ 航班候选结果可复用
  ├─ 排序目标作废
  └─ 旧 Worker 标记 v1
  ↓
Plan v2：按价格排序
  ↓
旧 v1 异步结果晚到 → version mismatch → 丢弃
```

## 02-08. 简单问题和复杂问题怎么路由到不同模型？

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否真正理解任务分解、路由、多 Agent 协作不是“多开几个模型”，而是状态、责任、上下文、工具权限、取消与聚合的系统设计问题。面试官通常会追问失败时如何收敛、用户改口怎么处理、异步结果如何防止污染新计划。

### 2. 核心结论

用分层 Model Router：规则/轻量分类器先路由明显请求，复杂请求交给强模型；运行过程中再依据失败、步数、验证结果动态升级。风险等级要和复杂度分开。

### 3. 深入原理：从概念讲到机制

复杂度不是看字数，而看多步依赖、工具数量、长上下文、推理强度、歧义、跨数据源等。生产上更可靠的是 Router + Cascade：先用便宜模型尝试，若出现低置信、grader 失败、重复 Tool、step budget 超限，再升级模型。长任务还可以 Step 级路由：Planner 用强模型，格式化/抽取用小模型。

* 模型路由要分三层：静态规则、轻量 Router、运行时 Escalation。复杂度不是看字数，而看多步依赖、工具数量、长上下文、推理类型、风险、历史失败和验证难度。
* 最稳的是 Cascade：先用便宜模型处理，若出现低置信、grader fail、tool loop 过深、复杂规划需求，再升级强模型。这样不要求 Router 第一次就 100% 判断正确。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 每次路由要记录 route\_reason、selected\_model、fallback\_count、cost、success，建立“路由决策→任务结果”的评测集，才能持续调阈值。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

结合你现在的架构，可以把 nanobot 作为 Agent Runtime，Java/Spring 保留业务 Service、事务和权限。需要平台级增强时优先放在 AgentDock/Gateway/Tool Adapter/Harness，而不是把所有逻辑塞回 Prompt。

### 6. 失败模式与 Trade-off

* 拆了很多 Agent 但没有明确 owner 和共享状态。
* 所有角色都拿全量上下文和全量工具，成本和权限面一起爆炸。
* 异步结果没有版本号/任务号，用户改口后旧结果仍写回。
* 高风险不等于高复杂；风险应单独进入 policy，不能因为问题简单就允许小模型直接执行退款。

### 8. 面试官可能继续追问

为什么不全部用最强模型？——成本、P99、吞吐和限额。 为什么不只做一次复杂度分类？——很多复杂性只有执行后才暴露。 高风险是否一定用最强模型？——不一定，风险主要增加代码约束/HITL，不是单纯增加模型智力。

* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

我会做规则 + 轻量 Router + 运行时升级三层。复杂度决定模型能力，风险决定约束强度；Agent 长任务再做 Step 级路由。nanobot 目前不自带这套复杂度路由，我会在平台层补。

### 1. 面试官真正考什么

看你是否真正理解任务分解、路由、多 Agent 协作不是“多开几个模型”，而是状态、责任、上下文、工具权限、取消与聚合的系统设计问题。面试官通常会追问失败时如何收敛、用户改口怎么处理、异步结果如何防止污染新计划。

### 2. 核心结论

MCP 解决 Agent↔Tool/Resource 的能力连接；A2A 解决 Agent↔Agent 的任务委托与生命周期。两者交互语义不同。

### 3. 深入原理：从概念讲到机制

工具调用通常是相对确定的 request/response；Agent 委托可能持续更久、需要进度、追问、取消、任务状态。把二者硬塞一个协议会让简单 Tool 调用背负复杂任务生命周期。实际系统可以是主 Agent 通过 A2A 委托给专业 Agent，专业 Agent 再通过 MCP 调工具。

* MCP 主要解决“Agent/Host 如何标准化访问工具和资源”；A2A 解决“一个 Agent 如何把任务交给另一个独立 Agent/服务”。前者偏能力暴露，后者偏主体协作。
* 不能一个协议全包的根本原因是信任边界、生命周期和语义不同：Tool Call 通常是细粒度 RPC；Agent-to-Agent 可能是长任务、异步、可协商和带状态的协作。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 把模型输出变成结构化 contract，Runtime 校验后才进入执行。
* 为关键状态引入 run\_id / step\_id / version / status，使它可持久化、可恢复、可审计。
* 对有副作用行为增加 policy、幂等、deadline、trace 和明确的 failure type。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。

### 5. 结合 nanobot / Java / 实际项目

结合你现在的架构，可以把 nanobot 作为 Agent Runtime，Java/Spring 保留业务 Service、事务和权限。需要平台级增强时优先放在 AgentDock/Gateway/Tool Adapter/Harness，而不是把所有逻辑塞回 Prompt。

### 6. 失败模式与 Trade-off

* 拆了很多 Agent 但没有明确 owner 和共享状态。
* 所有角色都拿全量上下文和全量工具，成本和权限面一起爆炸。
* 异步结果没有版本号/任务号，用户改口后旧结果仍写回。

### 8. 面试官可能继续追问

* 如果这个方案失败，系统最后会收敛到什么状态？
* 哪些属于模型软决策，哪些必须由代码硬约束？
* 你会用什么离线/线上指标证明这个设计真的更好？

### 9. 1～2 分钟口述版

面试时先给结论，再说明核心机制和失败边界，最后用实际项目说明你会如何落地。不要从术语定义开始铺满两分钟。

## 02-14. Multi-Agent 除了 Handoff，还有哪些通信方式？怎么选？

> 标签：理论、工程、实践

### 1. 面试官真正考什么

看你是否真正理解任务分解、路由、多 Agent 协作不是“多开几个模型”，而是状态、责任、上下文、工具权限、取消与聚合的系统设计问题。面试官通常会追问失败时如何收敛、用户改口怎么处理、异步结果如何防止污染新计划。

### 2. 核心结论

常见通信有结构化消息、共享黑板/Task Store、Artifact/File 引用、事件总线、函数式委托和 Agent-to-Agent 任务协议。选择取决于状态规模、时延和耦合度。

### 3. 深入原理：从概念讲到机制

小规模同步协作可直接结构化 message；大产物用 artifact reference；多消费者/长任务用 event bus；需要任务生命周期和跨系统 Agent 协作时再考虑 A2A。不要让 Agent 互相复制完整 history。

* Handoff 最大难点不是“把对话转给另一个 Agent”，而是传递最小但完整的任务状态：goal、用户约束、已完成步骤、关键 evidence、未解决问题、权限和 deadline。

### 4. 工程落地：代码/状态/数据结构应该怎么设计

* 接收方必须知道哪些事实是 verified、哪些是模型推断；否则总结中的幻觉会在 Agent 间传播并放大。

**建议落地检查：** 能否回答“状态放哪、谁能改、失败后怎么恢复、旧结果怎么识别、怎么评测”？如果不能，说明方案还停留在概念层。
